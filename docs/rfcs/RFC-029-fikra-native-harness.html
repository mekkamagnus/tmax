1. Summary

Fikra-mode is spec-complete as designed (RFC-013/RFC-027, issues #206–#225): chat, threads, checkpoints, tree-diff revert, worktree isolation, L1/L2 approvals, FAEP events, two CLI backends. This RFC analyzes what remains to make it a full AI harness in its own right — the peer of Claude Code or Pi — rather than an orchestration and safety layer wrapped around other harnesses' CLIs.

The finding: three load-bearing gaps (a native model backend, an own tool system, an own agent loop) plus six secondary ones. Everything needed at the primitive level already exists in tmax (http-request, make-process, signal, buffer ops). The conventions follow current harness standards: AGENT.md for project memory, a .fikra/skills/ folder for skills.

2. The architectural fact

Fikra today is a harness around harnesses. Its backends are complete agent CLIs (Claude Code, Codex) invoked per turn via claude --print --output-format stream-json --resume …. The agent loop, tools, context management, and permissions all live inside the wrapped CLI. Fikra contributes UI, threads/projects, checkpoints, and an approval bridge (L2 rides the CLI's --permission-prompt-tool hook where available).

 fikra today:                          target ("like Claude Code/Pi"):

 you -> chat -> claude CLI              you -> chat -> native model API
                |                                        |
                | (loop, tools,                          v
                |  perms INSIDE CLI)              fikra agent loop (T-Lisp)
                v                                        |
        checkpoints, revert,                       tool_use request
        worktrees, approvals                              |
        (bridged via MCP hook)                    fikra tools execute:
                                                      buffer-edit, bash,
                                                      search, web
                                                        |
                                                        v
                                              checkpoint -> approve (L2)
                                              -> execute -> tool_result
                                              -> loop until done

The right side makes fikra's safety machinery per-action instead of per-turn — which is what the L2 design was built for. Today it can only gate the wrapped CLI through a single hook; with native tools, every edit, command, and search passes through checkpoint → approval → execution.

4. The three load-bearing gaps

4.1 Native backend (capability 8)

An adapter that talks directly to a model API over the existing http-request primitive, parses the response stream, and normalizes to FAEP events. This is what removes the dependency on another harness being installed. Ollama (localhost, no key) is the natural first target; Anthropic/OpenAI follow.

4.2 Own tools (capability 9)

A tool registry + executor in T-Lisp. The natural toolset is nearly free because the host is an editor:

  • buffer-read / buffer-edit — atomic, checkpointable, and visible in the UI as buffer changes (the editor is the tool surface)
  • bash — via make-process, streamed
  • search — rg via make-process
  • web — via http-request

Tool schemas (what the model sees) and result formatting (what the model gets back) are the work.

4.3 Agent loop (capability 10)

The turn state machine becomes: send → stream → on tool_use: checkpoint → approve (L2) → execute → tool_result → send again, until a stop-condition or budget. Abort already exists (signal). This loop converts fikra's safety design from per-turn to per-action enforcement — the original design intent, finally load-bearing.

6. What fikra would have that Claude Code doesn't

  • The whole harness is user-rewritable in T-Lisp while it runs. Claude Code needs its own extension mechanisms; fikra is the environment.
  • Per-action git checkpoints with tree-diff revert of AI work.
  • Per-thread worktrees as the isolation unit.
  • A real editor as the tool surface — edits land in buffers the user is looking at.

9. Open questions

  1. Streaming transport: http-request today is request/response. Token streaming needs either a chunked/SSE-capable primitive or a buffered non-streaming loop first. Which for P1?
  2. Tool schema format: mirror the major-provider JSON tool schema verbatim, or a T-Lisp-native description normalized at the adapter boundary?
  3. Skills execution: SKILL.md bodies are prompts for the model; defworkflows are T-Lisp programs. One mechanism or two, and how do they compose?
  4. Concurrency model: does the agent loop run on the daemon's editor thread (simple, blocks no one?) or per-thread processes (matches the worktree isolation)?
  5. L2 degradation: with native tools, approvals no longer depend on the CLI's --permission-prompt-tool — does L2 become the default runtime mode?
